TASK 1 — CI/CD CONCEPTS

1. Continuous Integration (CI) is the frequent integration of small changes with automated build and test checks. It discovers integration problems close to the change that caused them.

Continuous Delivery keeps every change that passes CI in a deployable state, but a person or release process decides when production deployment happens. Continuous Deployment goes further by automatically deploying every passing change to production.

2. A broken endpoint can reach main; CI tests catch regressions before merge. A committed API key can go unnoticed; secret scanning identifies it. A dependency with known vulnerabilities can be merged; dependency scanning consistently finds it. Manual review can be inconsistent and slow; repeatable checks give each pull request the same baseline and rapid feedback.

3. Security checks should run on a pull request before merge so the author can correct a problem while it is isolated from the shared main branch. This is shift left: it moves validation earlier, where remediation costs less and affects fewer people. Scanning only after a push to main identifies the risk after it is already in the team branch.

4. A workflow is YAML-defined automation in GitHub Actions. A job is a set of steps run by a runner. A step is one command or action in a job. A runner is the machine that executes a job. An action is reusable packaged automation used in a step.

5. A laptop audit depends on a person remembering to run it, using the current lockfile, and reporting its result. A pipeline executes the same command for every relevant push and pull request in a clean runner and leaves an auditable result. Because it can fail, branch protection can enforce it rather than treating it as advice.

TASK 3 — SECRET DETECTION

1. A secret deleted in a later commit is still compromised because the original value remains in repository history and may already have been copied, cached, or cloned. It must be considered exposed and rotated or revoked.

2. I chose Gitleaks in .github/workflows/secret-detection.yml. It scans pushes and pull requests and provides repository-history scanning even when the GitHub plan has no push protection.

3. Gitleaks failed-run URL and log: [replace after a disposable-branch demonstration]. The demonstration must contain an invented credential only and be removed after evidence is captured.

Response process: (1) immediately revoke or rotate the exposed credential; (2) remove it from current code/configuration; (3) investigate repository history, logs, and use; (4) invalidate affected sessions/resources and create a replacement secret; (5) document the incident and improve controls. Revocation comes first because removing text from Git does not stop someone who already holds a usable secret.
